# Контракт атомарной задачи — Лунора

Фиксированный документ. Форма, по которой агент **берёт** работу.
Задача без этого контракта не берётся: сначала контракт, потом работа.

Дисциплина слайса (PASS как команда, `WORKLOG`, загрузочная последовательность) —
в `LUNERA_STANDARDS.md` §3.1. Здесь — про задачу и про роли.

---

## 1. Зачем контракт

Без формы задачи агент получает «сделай X» и делает X как умеет: слишком много,
слишком мало, в чужих файлах, без проверки. Контракт делает три вещи:

- **задачу атомарной** — один артефакт, одна проверка, один исполнитель;
- **границы явными** — что агент вправе менять, а что не вправе;
- **проверку заданной заранее** — агент не придумывает критерий готовности
  под свой результат, а берёт его из контракта.

## 2. Семь полей

```
TASK      : <атомарная операция; один изменяемый артефакт>
ВХОД      : <контракт / документ / код, из которого работать>
ГРАНИЦЫ   : <файлы, которые можно менять; всё остальное — read-only>
ПРОВЕРКА  : <команда, которой агент пользуется как приёмкой>
КРИТЕРИЙ  : <как понять, что готово; PASS = зелёный выход ПРОВЕРКИ>
СКИЛЛ     : <скилл, который обязателен к применению>
РЕВЬЮ     : <кто ревьюит, что именно смотрит>
```

| Поле | Требование |
|---|---|
| `TASK` | одна операция; результат — один файл, одна функция, один документ |
| `ВХОД` | конкретный источник, а не «сделай как надо» |
| `ГРАНИЦЫ` | явный список файлов на запись; пустой список = только чтение |
| `ПРОВЕРКА` | **исполняемая команда**; «посмотреть глазами» — не проверка |
| `КРИТЕРИЙ` | формулировка, которую можно проверить, а не «выглядит хорошо» |
| `СКИЛЛ` | явное имя; без него агент изобретёт свой подход |
| `РЕВЬЮ` | роль и предмет ревью; ревью — не «посмотреть diff», а конкретный вопрос |

## 3. Тест на атомарность

Задача атомарна, если на все шесть вопросов ответ «да»:

1. **Один артефакт на выходе.** Если результат — «и ещё, и ещё» — это не задача.
2. **Есть команда проверки.** Нет команды — критерий придумают под факт.
3. **Задача не трогает чужие файлы.** Всё, что не в `ГРАНИЦЫ`, — read-only.
4. **Задача помещается в одну сессию исполнителя** (ориентир: 15–90 минут работы).
5. **Результат можно принять или отклонить однозначно.** «Ну, вроде работает» — не критерий.
6. **Понятно, кто следующий.** Задача без следующего шага — подготовительная, а не атомарная работа.

Если хотя бы один ответ «нет» — задача декомпозируется дальше. **Недекомпозированная
задача не выполняется, а уточняется.**

## 4. Правило потребителя (против бюрократии)

Артефакт — документ, отчёт, лог — **существует, пока у него есть названный
потребитель и конкретный вопрос, на который он отвечает**.

- Нет потребителя → артефакт удаляется, а не улучшается.
- Два артефакта с одним и тем же вопросом → один лишний, удаляется.
- Документ без потребителя — это не «заготовка на будущее», это налог на внимание.

Закрытие гейта = **доказательство**, а не отчёт о проделанной работе:
`gates/<gate>-CLOSED.md` со SHA. Пересказ работы — не документ.

## 5. Кто что делает

| Действие | Кто |
|---|---|
| Декомпозиция гейта в атомарные задачи | система (оркестратор) |
| Утверждение разбивки | **оператор** — один раз, до начала работы |
| Выполнение задачи по контракту | агент-исполнитель |
| Ревью результата | независимый ревьюер (по `REVIEWER_CHARTER.md`) |
| Приёмка задачи | система — по зелёной проверке |
| **Закрытие гейта** | **оператор** — всегда |
| Продуктовое решение (что делаем, как должно работать) | **оператор** — всегда |

Автономия системы: закрытие **задачи** внутри гейта. Закрытие **гейта** —
всегда за оператором. Этот уровень автономии меняется только осознанным решением.

## 6. Формат файла задачи

Задача живёт в файле, а не в переписке: `docs/current/tasks/<task-id>.md`.
Поля §2 — в том же файле. Файл переживает сессию: потерял сессию — поднял
файл и продолжил.

Каждая задача вправе завести **свой** документ только по правилу потребителя
(§4) — то есть если этот документ отвечает на вопрос, который не отвечает
ни один существующий.
