# Публичный API и доменные схемы

**Назначение:** зафиксировать контракт, по которому клиенты (Telegram/MAX/веб/мобильные) общаются с движком, и канонические доменные схемы, на которые опираются и backend, и frontend. Выполняет требование ADR-002 («контракт публичного API — отдельный артефакт») и замечания ревью A14, A15, A20, A21.
**Статус:** контракт v0.1, draft. Числовые лимиты и часть ошибок помечены `[уточнить]`.
**Связано:** `ADR-002-клиенты-и-движок.md`, `ARCHITECTURE.md` §1–§3/§5/§10, `ENGINE-SPEC-РАСЧЕТ.md` §1/§7, `data-model.md`, `TRANSACTIONS-КОНТРАКТЫ.md`.

---

## 0. Принципы

- Три слоя **Клиенты → API → Движок**. Клиент видит **только схемы API**, не доменные типы ядра.
- API **версионируется** (`/v1/…`); несовместимые изменения → новая версия, старые клиенты продолжают работать.
- Долгие операции — **асинхронные**, через ресурс операции с наблюдаемым статусом (расчёт карты, сборка разбора, генерация в чате).
- Владелец любого объекта берётся **из сессии**, не из тела запроса.
- Все обращения к ПДн — только после согласия нужной категории (см. `legal/ПРАВОВЫЕ-ТЕКСТЫ.md`).

> **H12.** Это полный перечень намерений; поля ответов `ChartView`/`DocumentView`/`ThreadView`, точные ошибки по каждому эндпоинту, пагинация списков и способ возобновления async после перезапуска клиента **детализируются в OpenAPI первым этапом разработки (эпик E8)** — до параллельной работы клиента и сервера. **Bootstrap нового пользователя — один атомарный первый запрос с согласием** (не `sessions`→`consents`→`charts` по отдельности): согласие и создание профиля фиксируются вместе.

### 1.2 Ресурс операции (async)

```
Operation:
  id, kind (chart_compute | document_build | chat_answer | export | deletion)
  status: queued | running | done | failed | canceled
  progress?            # для labour-illusion
  result_ref?          # ссылка на готовый объект при done
  error?               # {code, message} при failed
  revision             # ревизия входа/контента, под которую посчитано
```
Клиент опрашивает `GET /v1/operations/{id}`; после перезагрузки приложения возвращается к ожиданию по тому же id. Результат **всегда** доступен в приложении независимо от доставки ботом (см. `TRANSACTIONS-КОНТРАКТЫ.md` §6).

### 1.3 Сквозные правила

- **Авторизация:** серверный токен сессии в заголовке; платформенная подпись (`initData` для Telegram) проверяется только при открытии сессии, дальше наружу не торчит.
- **Идемпотентность:** клиентский `Idempotency-Key` привязан к `(account, тип операции, хеш тела)`; тот же ключ с другим телом → `409 idempotency_conflict`. Ключи платежей/выдачи — серверные (`TRANSACTIONS-КОНТРАКТЫ.md` §3–§5).
- **Лимиты:** rate-limit на аккаунт и на IP `[уточнить]`; на длину вопроса; суточный/попакетный лимит расхода LLM (§5).
- **Ошибки:** единый конверт `{error:{code, message, retriable, details?}}`; `code` — из общего enum (ниже).

## 2. Доменные схемы (канонические)

Эти схемы — источник правды и для API, и для макетов. `data-model` поднимается до **v3.1**: поля ниже в основной схеме, не в примечаниях.

### 2.1 `InputSnapshot`
| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `birth_date` | date | да | **Явная дата рождения, независимо от точности времени.** При `moment=None` расчёт идёт по дате (деградация) |
| `time` | time? | нет | местное время; отсутствие — штатный случай |
| `time_precision` | enum(`exact`,`approx±`,`range`,`unknown`) | да | допуск времени |
| `place` | `{place_id}` | да | **единый ключ справочника мест** (`place_id`, §4.4/§6.2 архитектуры). `lat/lon`, IANA-зона, `historical_name`, `gazetteer_build` — **выводятся сервером** из `place_id`, клиент их не передаёт (защита от подмены координат). Выбор только из справочника; точный адрес/внешний геокодер — лишь после согласия (О-9, §4.4) |
| `sex` | enum(`f`,`m`) | да | нужен для направления да-юнь (Ба-Цзы) |
| `names` | `{at_birth, current?, planned?, patronymic?}` | да | ФИО для нумерологии |
| `method_profile_version` | string | да | внутренний профиль «Лунора» (§6 ENGINE-SPEC) |

### 2.2 `Signal` (выход движка)

⚠️ **H11 — единые канонические имена.** Имена ниже совпадают с `data-model` и `ENGINE-SPEC-РАСЧЕТ` (одна доменная схема). Публичный DTO отдаёт их 1:1. Прежние расхождения сняты: `system` → **`system_id`**, `lunora_rule` → **`lunora`**, кадр `bazi/numerology` → **`none`**. Полный интервал неопределённости (`values/flips_at/depends_on`) живёт в доменном `ChartSnapshot`; в `Signal` — только тег `stability`.

| Поле | Тип | Описание |
|---|---|---|
| `id` | string | стабильный идентификатор сигнала |
| `system_id` | `SystemId` = `western` \| `vedic` \| `bazi` \| `numerology` (единый enum, §6) | школа-источник |
| `frame` | enum(`tropical`,`sidereal`,`none`) | кадр (как в ENGINE-SPEC §8.4 Р-1); для Ба-Цзы/нумерологии — `none` |
| `doctrine_family` | enum(`planetary`,`chinese`,`numerological`) | семейство доктрины — **детерминированная функция `system_id`** (western,vedic→`planetary`; bazi→`chinese`; numerology→`numerological`, `ENGINE-SPEC-РАСЧЕТ.md` §8.4 Р-1); согласие засчитывается **только между разными семействами** |
| `value` | any \| `not_computed` | значение либо `not_computed` |
| `reason` | string? | причина `not_computed` / воздержания |
| `stability` | enum(`stable`,`range`,`undetermined`,`convention`) | тег интервальной неопределённости (полный объём — в `ChartSnapshot`) |
| `can_vote` | bool | участвует ли в голосовании (fail closed) |
| `rule_origin` | enum(`source`,`lunora`) | «правило Луноры» называется авторским |
| `versions` | `{engine, rules, ephemeris, tz_build}` | версии, под которые посчитано |

### 2.3 Прочие
- `ChartSnapshot` — неизменяемый результат расчёта; `chart_id` (случайный, §9 TRANSACTIONS), `calc_fingerprint` (внутренний).
- `NarrativePlan` — что и в каком порядке сказать; для каждого блока — допустимый набор `claim_refs`.
- `ClaimView`, `ThemeView`, `DocumentView` — то, что видит клиент (без внутренних типов ядра).

### 2.4 Единый enum статусов/причин
`status`: `queued|running|done|failed|canceled|stale|deleting`.
`error.code`: `invalid_input|consent_required|not_owner|paywall|idempotency_conflict|product_unavailable|expired_link|reconcile_needed|rate_limited|internal`.

## 3. Доступ к объектам (A15)

- **Владелец — из сессии.** Каждое обращение к `Person`, заказу, операции, документу, переписке, экспорту проверяет `owner_id == session.account` и область права. Фоновые задания получают объект только с проверкой владельца.
- **Выдача файлов (PDF, экспорт):** короткоживущие подписанные ссылки (`expired_link` после срока `[уточнить]`); не превращаются в постоянный публичный доступ.
- **Шеринг:** ссылка открывает **только данные владельца**; артефакты с ПДн второго человека исключены из шеринга и экспорта; совместимость показывается обезличенно.
- **Роли оператора:** админка (возвраты, снятие доступа) — отдельная роль с журналом; клиентский API таких прав не даёт.
- **Журналирование:** доступ к объектам и админ-действия логируются **без значений ПДн** (тест на форматтер и трекер, `TRANSACTIONS` §7).
- **Приёмка:** отрицательные тесты на чужой `id` во всех ручках и заданиях; отозванная сессия не работает.

## 4. Правило импортов на границе API

Инвариант ARCHITECTURE §2.3 — односторонний (`core/*` не импортирует `app/adapters/api`). Добавляется **обратный смысл**: наружу (в клиент) отдаются только схемы API (`api/schemas`), доменные типы ядра (`Signal`, `ChartSnapshot`, внутренние поля) за границу API **не выходят**. Проверяется тем же линтером импортов + схемным слоем сериализации. Так «клиент не видит внутренности» — не декларация, а инвариант.

## 5. Политика получателей LLM (A21)

- Доступ к модели — только через `LLMPort` и **один контролируемый выход**; через него идут ВСЕ вызовы: генератор, модель-судья, извлечение памяти.
- **Профиль маршрутизации** (версионируемый): разрешённые провайдеры и модели (OpenRouter + явный выбор провайдера), условия fallback, параметры структурированного ответа (JSON-схема `NarrativeRender`), `temperature ≤ 0.3`, лимит токенов, тайм-ауты, лимит стоимости. Неизвестный провайдер/маршрут — отклоняется.
- **Данные:** в пакет идёт только LLM-safe класс (без ФИО/даты/места); детерминированный класс подставляется кодом после валидатора (ARCHITECTURE §5.6, B4). ⚠️ «Обезличенные выводы без ФИО» — это **деперсонализация, не обезличивание** (ст. 3 152-ФЗ): принадлежность восстанавливается оператором, поэтому защита строится **не** на доводе «это не ПДн», а на согласии + договоре с получателем (запрет хранения/обучения).
- **Трансгран:** OpenRouter зарубежный (D-114) → процедура ст. 12; профиль маршрутизации не должен уводить пакет к незаявленному получателю через fallback.
- **Смена модели** меняет не только цену, но и формат/качество проверки — поэтому фиксируется в `ContentRelease` и регрессе промптов.

## 6. Расширяемость школ

**Единый enum `SystemId` = `western` · `vedic` · `bazi` · `numerology`** — одинаково в `API-КОНТРАКТ` §2.2, `ENGINE-SPEC-РАСЧЕТ` §1.2, `data-model` и `versions.engine`. Прежний разнобой (`western_astrology`/`jyotisha` в одних местах, `western`/`vedic` в других) снят H11. Школа — модуль, зарегистрированный в реестре движка, который выдаёт `Signal[]` в общем формате. **Добавление школы = регистрация модуля + её правила голоса и блоки; ядро интерпретации, ключи кэша и API не меняются.** Ключи кэша не должны содержать жёсткого перечисления школ.

## 7. Веб и мобильные клиенты

Сейчас identity и доставка привязаны к Telegram (`initData`, `PLATFORM_IDENTITY`, доставка ботом). Чтобы веб/мобильный клиент подключались **без правки движка и схемы БД** (как обещает ADR-002):
- **AuthPort** — несколько реализаций (Telegram `initData`, MAX, веб-вход по e-mail/OTP, мобильный). Аккаунт — платформо-независимая сущность; платформенная идентичность — отдельная связь `PLATFORM_IDENTITY (account_id, platform, external_id)`, многие-к-одному.
- **DeliveryPort** — доставка результата каналом клиента (бот Telegram, push MAX, web-push, e-mail); результат всегда есть в приложении независимо от канала.
- **PaymentPort** — СБП/ЮKassa одинаково для всех каналов; привязка платежа к аккаунту, не к платформе.
- ✅ **РЕШЕНО H13/D-119. В v1 — только Telegram.** Запасной вход (e-mail/OTP) и связывание аккаунтов Telegram↔MAX **отложены** до веб/мобильной версии (докручиваются через `AuthPort` без правки движка и БД).
- **Восстановление доступа при потере Telegram (v1)** — **вручную через поддержку**, с подтверждением владения аккаунтом (данные профиля, история платежей у провайдера и т.п.). Одного `order_id` или чека **недостаточно**. Это явное ограничение v1 (фиксируется в оферте и `ОПИСАНИЕ-ПРОЕКТА`). Результат всегда доступен в приложении (не только доставка ботом), поэтому после восстановления доступа покупки на месте.
