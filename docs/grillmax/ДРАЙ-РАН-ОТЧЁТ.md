# Dry-run П3: поздняя смена модели оплаты (по рекомендации второго ревью)

**Дата:** 2026-11-19 · **Полигон:** копия пакета «Лунора» в песочнице (реальные файлы не менялись).

## Что проверяли
Рекомендация ревьюера: внести изменение решения на поздней стадии (после G9/G10) и убедиться, что механизм П3 подсвечивает **все** затронутые контракты, прототип, экономику и дорожную карту.

## Сценарий
1. База: `D-121` (Stars + ЮKassa/СБП) активно, донесено во все зависимые. Прогон чекера — по категориям распространения **чисто**.
2. Инъекция поздней правки: модель оплаты меняется снова — `D-140` (только CloudPayments, ЮKassa убрана) заменяет `D-121`. **Документы намеренно не обновлены** (имитация неполного переноса). Ревизия G5 сдвинута rev-2 → rev-3.
3. Повторный прогон `tools/check-consistency.py` (режим project).

## Результат — механизм поймал всё затронутое

| Категория | Поймано | Что это |
|---|---|---|
| `decision-not-propagated` | **6** | `D-140` не донесён ни до одного зависимого (описание, транзакции, архитектура, дорожная карта, блокеры, прототип) |
| `cancelled-referenced` | **12** | `D-121` (отменённое) всё ещё упомянут как действующий — включая **контракты** (TRANSACTIONS, API), **прототип** (wireframes/02-report.html), **экономику** (ПРАЙС), spec/payment, передачу команде |
| `artifact-stale` | **1** | визуальный артефакт G9 собран на G5=rev-2, текущая G5=rev-3 → требует повторной приёмки |

Итого машина подсветила **19 мест** одной правкой, в т.ч. файлы за пределами объявленного списка зависимых (их поймал контроль отменённого решения по тексту). Это ровно класс «хвост после правки», ради которого и строился П3.

## Честная граница (что машина НЕ делает)
- Машина ловит **форму**: присутствие/отсутствие ID решения, упоминание отменённого как действующего, рассинхрон ревизий. Она **не** пересчитывает экономику в ПРАЙС и не проверяет, что новые комиссии CloudPayments корректно отражены в unit-экономике — это **смысловая** проверка агента в `CONSISTENCY_REPORT.md`.
- Если затронутый файл **не упоминает** ID решения и **не** в списке зависимых — машина его не увидит. Поэтому список `dependents` в реестре должен быть полным, а смысловой проход агента — обязателен (без него exit П3 не засчитан).

## Вывод
Машинная половина П3 **работает end-to-end**: поздняя смена платёжного решения подсвечивается по всему пакету за секунды. Побочно подтвердилась правка дизайна: `unknown-decision-id` блокирует только при `registry_complete: true` (иначе тонет в реальном проекте с десятками решений).

Критерий ревьюера — «агент не может получить GO при устаревшем критическом артефакте или непротранслированном решении» — на этом сценарии выполняется: 40 блокирующих, exit 1, GO невозможен.
