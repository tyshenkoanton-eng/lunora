# ADR-002. Границы: движок, API, клиенты, расширяемость школ

**Статус:** принят (2026-11-16, решение Антона) · **Контекст:** G9
**Связанные решения:** D-037 (отделение ядра от платформы), D-112 (LLM через OpenRouter), D-113

## Решение

Система строится из **трёх независимых слоёв** с односторонней зависимостью: **Клиенты → API → Движок**. Нижний слой ничего не знает о верхнем.

```
Клиенты (сменные, тонкие)        API (стабильный контракт)        Движок (ядро)
┌───────────────┐
│ Telegram Mini │──┐
├───────────────┤  │          ┌──────────────────┐          ┌─────────────────────────┐
│ MAX Mini App  │──┼────────▶ │  Публичный API   │────────▶ │ Расчёт → Интерпретация  │
├───────────────┤  │          │ (версионируемый) │          │ → План → Синтез (LLM)   │
│ Веб-сайт      │──┤          └──────────────────┘          └─────────────────────────┘
├───────────────┤  │                                                     │
│ Моб. прил.    │──┘                                          школы — сменные модули
└───────────────┘                                            за общим контрактом
```

## Почему так

Цель Антона: **подключение нового клиента не переписывает движок**, и **добавление школы не ломает остальные**. Это два разных измерения расширяемости, и их надо развести явно.

### 1. Движок не знает, кто его клиент
- Движок принимает данные о рождении и отдаёт разбор. Он **не знает**, пришёл запрос из Telegram, MAX, веб-сайта или мобильного приложения.
- Всё платформенное (вход/авторизация, оплата, «поделиться», уведомления, тема оформления) — **не в движке**, а в тонком слое клиента/адаптера (D-037).
- Новый клиент = новый тонкий клиент против **того же API**. Движок не трогается.

### 2. API — стабильный контракт между клиентами и движком
- Клиенты общаются с движком только через **публичный API** (HTTP/JSON), а не напрямую с внутренними функциями.
- API **версионируется**: старые клиенты продолжают работать, когда внутри движка что-то меняется.
- Telegram/MAX Mini App — это тоже клиенты API (внутри одного процесса на старте это может быть прямой вызов, но **граница контракта та же**, чтобы веб и мобильные подключались без переделки).
- В API попадает только стабильное: «посчитай карту», «дай профиль/тему», «ответь на вопрос в чате», «статус доступа». Внутреннее устройство (какие таблицы, какие движки) наружу не торчит.

### 3. Школы — сменные модули за общим контрактом
- Каждая школа (западная, ведическая, Ба-Цзы, нумерология) — **отдельный модуль** за единым контрактом расчёта: `вход (дата/время/место/имя) → набор сигналов` (`InputSnapshot → Signal[]`).
- Интерпретация и голосование работают **с сигналами**, а не с внутренностями конкретной школы.
- **Добавить школу** = добавить модуль, который выдаёт сигналы в том же формате, + её правила голоса и блоки библиотеки. Остальные школы, движок интерпретации и клиенты **не меняются**.
- Это же даёт «мягкое» отключение: школа, у которой величина не вычислима (`can_vote: false`, §0.3 ENGINE-SPEC), просто молчит — система не ломается.

## LLM через порт (D-112)

- Доступ к языковой модели — через **`LLMPort`** (один интерфейс), а не прямые вызовы провайдера из кода.
- **Текущий провайдер — OpenRouter** (рабочее решение для разработки): один ключ, много моделей, легко сравнивать и переключать.
- ⚠️ **Юридическое следствие:** OpenRouter — зарубежный сервис, значит обращение к нему = **трансграничная передача ПДн**. Остаточный канал (текст вопроса, память) требует режима ст. 12 152-ФЗ: уведомление Роскомнадзора, либо переход на российского провайдера к запуску (см. `ИССЛЕДОВАНИЕ-ПРАВО.md`). Порт `LLMPort` позволяет сменить провайдера **без переписывания движка** — это и есть страховка.

## Что из этого следует (к реализации)

- Зафиксировать **контракт публичного API** (эндпоинты, форматы запроса/ответа, версия) как отдельный артефакт — на него опираются все клиенты.
- Контракт школы (`Signal`) и контракт `LLMPort` держать стабильными; менять — только через версию.
- Клиенты (Telegram, MAX, веб, мобильные) — в отдельных пакетах/репозиториях, в движок не импортируются.
- Granica «что в API / что внутри» проверяется тем же правилом импортов, что и в ARCHITECTURE §2.3.

## Последствия

- Плюс: новый канал (веб, мобильное приложение, ещё одна площадка) добавляется без риска для расчёта; новая школа — локально; смена LLM-провайдера — одна точка.
- Цена: нужно заранее спроектировать и держать **стабильный API-контракт** — это небольшая дополнительная дисциплина на старте, окупается при каждом новом клиенте.
