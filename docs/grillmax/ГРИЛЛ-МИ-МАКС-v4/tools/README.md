# Инструменты ГРИЛЛ МИ МАКС

## `check-consistency.py` — референс-чекер связности и распространения решений

Машинная половина предохранителя **П3** (смысловую проверку по существу агент делает сам — см. SKILL.md). Портативный: специфику проекта читает из конфига, а не хардкодит. Только чтение.

```bash
python3 tools/check-consistency.py [корень] [--mode package|project] [--json]
python3 tools/test_check_consistency.py        # регрессионные тесты (13 кейсов повторного ревью)
```
По умолчанию корень — родитель `tools/`. Коды выхода: `0` нет блокирующих · `1` есть блокирующие · `2` корень не похож на пакет/проект.

### Два режима (определяются автоматически)
- **package** — методологический пакет (есть `SKILL.md`, нет `_SESSION.json`): ссылки, casefold, запретные термины. Реестр решений не требуется.
- **project** — живой проект (есть `_SESSION.json`): всё выше + **обязательный** реестр решений (пустой → блок), распространение, устаревание по ревизиям, конфликт реестров, неизвестные ID, валидность токенов.

### Что проверяет (машинно — только ФОРМА)
1. **Битые markdown-ссылки** (блок); ссылки вне пакета — инфо.
2. **Casefold-коллизии** имён (`ENGINE.md` vs `engine.md`) — блок.
3. **Распространение решений** (project): активное решение упомянуто во всех `dependents` (**точное** сравнение ID — `D-001` ≠ `D-0010`) — иначе `decision-not-propagated`; отменённое не встречается как действующее — иначе `cancelled-referenced`.
4. **Устаревание** (project): `input_versions` артефакта ≠ текущая `revision` входного гейта → `artifact-stale` (блок).
5. **Реестр**: канонический — `DECISIONS.md`; расхождение с `_SESSION.json` по статусу/значению → `registry-conflict` (блок). Дубли/неизвестные/невалидные статусы → блок. Битый `_SESSION.json` → блок.
6. **Токены**: `tokens.json`/`brand.tokens.json` парсятся и имеют ключ цвета.
7. **Запретные термины** — из конфига. **ID рисков** без определения — инфо.

Смысл (бизнес-правила, цены, инварианты) машина **не** проверяет — это вердикт агента в `CONSISTENCY_REPORT.md`. Без него exit П3 не засчитывается (см. П3 в SKILL.md).

### Конфиг (необязательный): `tools/grillmax-check.config.json`
```json
{
  "banned_terms": ["старый бренд", "устаревш\\w* модель оплаты"],
  "banned_scope_globs": ["**/*.html", "wireframes/**/*.html"]
}
```
- `banned_terms` — регулярки снятых терминов, которых не должно быть в видимом тексте (напр. после смены модели оплаты/бренда). Нет конфига — проверка пропускается.
- `banned_scope_globs` — где искать (по умолчанию `**/*.html`), чтобы не ловить сам термин в методическом описании.

### Реестр решений
Чекер читает решения из `_SESSION.json` (поля `id`, `status: active|superseded`, `dependents: [файлы]`, `superseded_by`) и/или из таблицы `DECISIONS.md`:
```
| ID | Значение | Источник | Зависимые | Версия | Статус |
|----|----------|----------|-----------|--------|--------|
| D-001 | <краткое значение решения> | G5 | 11_architecture.md, 16_roadmap.md | rev-2 | active |
```

### Важно
Машина ловит **форму** (ссылки, имена, присутствие ID, запретные строки). **Смысл** (одно бизнес-правило не противоречит другому, даже если числа совпали) проверяет агент и фиксирует вердикт — это требование exit П3. Чекер не заменяет внешнее ревью, но ловит класс «хвостов после правки» за секунды.

> Пример проектной настройки (с якорями и терминами конкретного продукта) — в рабочем проекте, не в методологическом пакете.
