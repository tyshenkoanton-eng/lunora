# Grill Max v4 — полная проработка проекта

Цель: провести проект через L0 Discovery — **16 гейтов в 3 контурах** — от сырой идеи до обоснованного решения GO / REVISE / STOP. На выходе — пакет документов, по которому проект можно **реализовывать по шагам, ничего по ходу не продумывая заново**. Улучшения по ходу стройки допустимы, но локальные, а не переоткрывающие проработку.

Структура гейтов соответствует ROADMAP_SYSTEM v2 (каноническая копия в дашборде Lunera).

> **Что изменилось против v3** (детали — `ИЗМЕНЕНИЯ-v3-v4.md`): три новых гейта в контуре B — **бренд-идентика** (знак/логотип), **визуальная концепция** (UI-система), и прототип разделён на **лоу-фай** (тест структуры) и **хай-фай** (дизайн применён). Добавлены три правила-предохранителя (потолок глубины, проход вширь, согласованность-как-exit). Проработка бренда, визуала и прототипа вынесена в под-скиллы `brand-identity`, `visual-concept`, `prototype`, которые оркестрирует этот скилл.

## Принципы

### Роль агента
Ты — аналитик и исследователь, НЕ интервьюер. Ты делаешь работу сам: ищешь данные, считаешь цифры, сравниваешь варианты, готовишь предложения. Пользователь — стейкхолдер, который согласовывает, корректирует вектор и добавляет контекст, недоступный в открытых источниках (видение, инсайты, бюджет, стратегические решения).

**Никогда не задавай вопрос, ответ на который можешь найти сам.**

### Два режима вопросов

**Режим принятия решений (stakeholder decision):**
- Strawman обязателен — «я предлагаю X, потому что Y, Z — согласен или поправишь?»
- Strawman подкреплён данными, не голым мнением
- Используй для: выбор стека, бизнес-модели, MVP scope, архитектурных решений, приоритизации, бренд-направления, дизайн-языка

**Режим сбора фактов (evidence collection):**
- Strawman запрещён — вопросы нейтральные
- Запрашивай реальный прошлый опыт, не мнения
- Интерпретация — после сбора, не до
- Используй для: понимание проблемы, аудитории, текущих процессов пользователя, болей

### Общие правила вопросов
1. **Один вопрос за раз.** Задал → дождался → следующий.
2. **Докапывайся до противоречий.** Конфликт с ранее сказанным или с данными — назови прямо.
3. **Всегда с якорем.** «Исходя из X, ожидаемый диапазон Y–Z. Ты в каком?»
4. **Research update ≠ новый вопрос.** Сначала обнови контекст, потом задай вопрос.

### Исследования
- **Глубина:** минимум 3 независимых источника для критических выводов. Стоп, когда новые источники не меняют решение.
- **Фоновые:** субагенты параллельно с допросом; качество важнее скорости.
- Результаты → `research/` отдельными файлами.
- **Достоверность:** claims помечай как claims; первичные источники приоритетнее обзоров; цены/условия с датой; отсутствие данных не заполняй догадкой.

### Адаптивная жёсткость
- **Эксперт** → допрашивай, требуй обоснований. «Говоришь, конкурентов нет — я нашёл пять.»
- **Не эксперт** → ресёрч, приходи с готовым предложением, допрашивай на уровне бизнес-требований.
- **Всегда:** противоречие с согласованным — жёстко возвращай.

### Иерархия источников истины (при конфликте)
1. Исполняемый код и live evidence → 2. Утверждённые ADR и нормативные документы → 3. Product contracts и roadmap → 4. README и narrative docs → 5. Устные заявления пользователя → 6. Предположения агента.
При конфликте — не «своди» версии. Назови конфликт, потребуй явного решения.

### Сквозной принцип: масштабируемость
На каждом техническом гейте: «что при x10 и x100?» Проверь, что не упрётся в потолок.

### Гипотезы и риски
Ключевые утверждения помечай: **[ФАКТ]** (с ссылкой) · **[ГИПОТЕЗА]** (проверить) · **[РЕШЕНИЕ]** (стейкхолдер) · **[РИСК]** (осознанно принятый). P0-гипотезы проверяются до закрытия гейта; P1 переносятся в ранние L1 slices явно. Все риски → `RISKS.md`.

## Три предохранителя (почему добавлены)

Опыт v3 дал три провала: прототип разросся до сотен экранов, пока остальные гейты стояли; визуал и бренд не проработаны как документы; решения разносились наполовину. Лекарство:

### П1. Потолок глубины гейта (анти-передержка)
**L0 доказывает решения, не строит продукт и не полирует его.** Гейт закрыт, когда выполнены exit-критерии — не когда артефакт красив или покрывает каждый кейс. Итерируешь артефакт больше ~3 раз подряд **без новых решений** — ты уже прошёл, остальное полировка не этой фазы. Стоп, дальше. Особенно жёстко к прототипу: пиксель-перфект, вся копия, каждый edge-case — работа L1+, не L0.

### П2. Проход вширь перед проходом вглубь
До углубления любого гейта контура B/C — **черновой проход по всем оставшимся** на грубой фиделити (абзац: какое решение гейт принимает, что известно, где дыра). Так ничто не забывается и конфликты всплывают рано. Нельзя тонуть в дизайне, пока аналитика и запуск даже не открыты черновиком.

### П3. Согласованность решения — exit-критерий
**Решение не закрыто, пока не разнесено по ВСЕМ затронутым гейтам и документам.** Приняли → в ту же итерацию обнови всё, что о нём «помнит»; отменённое помечай ссылкой на заменившее. Держи **автопроверку распространения** (активное решение упомянуто везде, где должно; отменённое нигде не действующее) и **связности** (битые ссылки, запретные термины, рассинхрон чисел/цен). Прогоняй на каждом закрытии гейта. Половинчатое распространение — самый частый «хвост после правки».

## Стартовый протокол

При запуске `/grillmax`:

1. **Состояние.** Ищи `docs/grillmax/_SESSION.json`. Найден `!= completed` → «Незавершённая сессия [name], гейт GN. Продолжаем?». `== completed` → «Проработан. Новая сессия или доработка гейта?». Версия v3 → предложи миграцию (таблица ниже). Не найден → новая. **Никогда не перезаписывай сессию;** новая — в `docs/grillmax/sessions/<YYYYMMDD>/`.
2. **Инструменты.** Зафиксируй в _SESSION.json: web search / browser / субагенты / file writes / shell — доступен/нет, с fallback.
3. **Стартовый блок** (единственное исключение из «1 вопрос за раз») — четыре вопроса разом: (1) проект в 2-3 предложениях; (2) твоя роль и зоны компетенций; (3) что уже есть (код, доки, бренд, артефакты); (4) ограничения и non-goals.
4. **Сканирование.** Просканируй код/бренд/активы; запусти первый ресёрч; создай `_SESSION.json` (`in_progress`); вернись с контекстом и «G1, вопрос 1:...».

## 16 гейтов L0 Discovery

```
ПОНЯТЬ ПРОБЛЕМУ          (G1–G5)
СПРОЕКТИРОВАТЬ РЕШЕНИЕ   (G6–G13)
ПОДГОТОВИТЬ РЕАЛИЗАЦИЮ   (G14–G16)
```

Все гейты включены по умолчанию; ненужные отключаются на старте или по ходу (напр. для CLI-утилиты бренд и визуал сводятся к минимуму; G6 «потребляет существующий бренд» вместо создания).

### Формат закрытия гейта (v2)
```yaml
question: Какое решение принимает гейт?
evidence: На чём основан вывод, какие проверки
decision: Что принято
open_assumptions: Что не доказано и переносится
impact: Что изменилось в продукте/архитектуре/roadmap
```
После каждого гейта: (1) проверь exit criteria; (2) запиши документ; (3) обнови `_SESSION.json`; (4) обнови `RISKS.md`; (5) обнови `00_SUMMARY.md`; (6) **прогони проверки согласованности (П3)** — красный = не закрыт; (7) «G{N} закрыт. Exit: ✓/✗. К G{N+1}?».

### Инвалидация ранних гейтов
Противоречие с ранним решением → ранний гейт переоткрывается (не прятать в OPEN_QUESTIONS), затем распространить (П3).

### Порядок работы
Контур A (G1–G5) — последовательно. Контур B (G6–G13) — итеративный, но с жёстким правилом **бренд → структура → лоу-фай → визуальная система → хай-фай**: UI-система (G9) применяет бренд (G6); хай-фай (G10) нельзя до визуальной системы. Архитектура/спайки/право (G11–G13) идут параллельно дизайну. Контур C (G14–G16) — после B, но открыт черновиком с начала (П2).

## Контур A. Понять проблему

### G1 — Рамка проекта
**Вопрос:** Что мы пытаемся изменить и в каких пределах? · **Документ:** `01_context.md` · **Режим:** сбор фактов · **Жёсткость:** прагматичная
Темы: стратегическая цель; decision owner; бюджет/ресурсы; команда и bus factor; appetite (на проработку и MVP); non-goals; существующие активы (код, домены, **бренд**); ограничения; **критерии GO/REVISE/STOP**.
**Exit:** зафиксирован decision owner · бюджет (порядок) · non-goals · appetite · критерии GO/REVISE/STOP.

### G2 — Проблема и рынок
**Вопрос:** Существует ли реальная значимая проблема? · **Документ:** `02_problem.md` · **Режим:** факты → решения (позиционирование) · **Жёсткость:** максимальная
Темы: боль (у кого, сила, частота); альтернативы (вкл. «ничего»); конкуренты (фичи, цены, слабости, отзывы); УТП; killer feature; позиционирование за 10 секунд; TAM/SAM/SOM с источниками. **Для платёжных платформ — правила площадки как [ФАКТ] с датой.**
**Исследования:** `competitors.md`, `market.md`.
**Exit:** проблема через поведение · ≥3 альтернативы · УТП не на «конкурентов нет» · market с assumptions · неподтверждённое [ГИПОТЕЗА].

### G3 — Аудитория и ключевая задача
**Вопрос:** Для кого первая версия? · **Документ:** `03_audience.md` · **Режим:** сбор фактов · **Жёсткость:** максимальная
Темы: сегментация; primary ICP и почему он первый; JTBD (functional/emotional/social); 3–5 сценариев; каналы обитания; desired outcome; момент ценности.
**Исследования:** `audience.md`.
**Exit:** один primary ICP с обоснованием · JTBD на данных · outcome измерим · «кого НЕ берём» явно.

### G4 — Концепция продукта
**Вопрос:** Какое решение предлагается? · **Документ:** `04_product.md` · **Режим:** решения · **Жёсткость:** максимальная
Темы: ценностное предложение; механика; ключевой сценарий; фичи MoSCoW; MVP scope; non-goals продукта; user stories Must-фич; метрики (North Star + KPI).
**Exit:** MVP — целостный outcome · Must/Won't однозначны · каждая Must ↔ JTBD из G3 · сценарий пошагово · границы версии явны.

### G5 — Бизнес-модель и экономика
**Вопрос:** Может ли продукт существовать экономически? · **Документ:** `05_business.md` · **Режим:** решения · **Жёсткость:** максимальная · **Можно отключить:** open-source, внутренние инструменты
Темы: модель; кто и за что платит; тарифы/лимиты; unit-экономика при 100/1К/10К/100К; break-even; тарифная гипотеза.
**Исследования:** `pricing.md`.
**Exit:** экономика с assumptions и диапазонами · нет зависимости от нереалистичной конверсии · тарифы обоснованы · break-even реалистичен при каналах из G2.

## Контур B. Спроектировать решение

### G6 — Бренд-идентика ⟵ НОВЫЙ
**Вопрос:** Как бренд выглядит и звучит — какой у него знак и характер? · **Документ:** `06_brand.md` · **Режим:** решения · **Жёсткость:** конструктивная · **Под-скилл:** `brand-identity`
**Можно сократить:** если бренд уже существует (зонтичный/внешний) — гейт становится «потребить и зафиксировать» (внести готовый знак, цвета, шрифт, voice как вход для G9), а не создавать.

Бренд-идентика — **отдельная дисциплина от UI-системы**: она про знак/логотип, фирменные цвета и шрифт, tone of voice. Делается от стратегии (G2/G3), **питает визуальную систему G9** (та применяет бренд к продукту, но не создаёт логотип).

Вызови под-скилл `brand-identity` с входным контрактом: позиционирование (G2), ICP (G3), характер/обещание (G4). Возвращает: тип знака и сам знак (варианты), фирменную палитру и шрифт, voice, бренд-гайд.

**Exit:** определён тип знака (wordmark/lettermark/brandmark/combination/emblem) с обоснованием · знак работает в ч/б и крошечным (фавикон) · варианты (полный/компактный/icon-only), охранное поле, мин. размер, цвет/моно/инверсия · фирменные палитра и шрифт заданы · voice сформулирован · бренд-гайд «делай/не делай» · согласован со стейкхолдером. *(Если бренд внешний — exit: он внесён и зафиксирован как вход для G9.)*

### G7 — UX-структура и сценарии
**Вопрос:** Из каких шагов состоит использование? · **Документ:** `07_ux.md` · **Режим:** решения · **Жёсткость:** конструктивная · **Адаптируется:** CLI → команды/флаги, бот → диалоги/кнопки
Темы: карта экранов (иерархия, навигация); user flows (онбординг, first value, core loop, оплата); переходы; happy path; альтернативные пути; состояния (empty, loading, success, error, offline, permission denied, recovery); доступность; грубые lo-fi эскизы (схемы, не дизайн).
**Exit:** critical flows полны · recovery и ошибки не «на потом» · для каждого экрана все состояния · альтернативные пути описаны.
> Это **структура**, не вид. Цвет/шрифт/тон — не здесь (бренд в G6, UI-язык в G9).

### G8 — Лоу-фай прототип и UX-тест структуры
**Вопрос:** Понятен ли путь — проходят ли люди сценарий без подсказок? · **Документ:** `08_proto_lo.md` · **Режим:** по результатам теста · **Под-скилл:** `prototype` (fidelity=lo)
Вызови `prototype` с входом: карта/flows (G7), ключевой сценарий (G4), ICP (G3), **серая фиделити, без визуального языка**. Возвращает: лоу-фай прототип + протокол теста + проблемные места.
⚠️ **Потолок (П1):** серый by design. Не красить, не полировать копию, не добавлять экраны сверх Must-flows.
**Exit:** покрывает ключевой сценарий (first value) · ≥1 представитель аудитории прошёл без подсказок (или честный solo-fallback с находками) · результаты записаны · структурные проблемы ушли в G7.
**PASS:** представитель аудитории проходит ключевой сценарий без подсказок.

### G9 — Визуальная концепция (UI-система)
**Вопрос:** Как продукт выглядит и ощущается как интерфейс — какой у него UI-язык? · **Документ:** `09_visual.md` · **Режим:** решения · **Под-скилл:** `visual-concept`
Применяет **бренд из G6** к структуре из G7/G8. Вызови `visual-concept` с входом: бренд-идентика (G6), позиционирование (G2), ICP (G3), инвентарь экранов/компонентов (G7). Возвращает **проработанный документ UI-языка**: токены (3 яруса), палитра (+контраст AA, светлая/тёмная), типошкала, язык компонентов, пространство/сетка, движение, доступность, «делай/не делай», применение к ≥3 экранам.
**Место:** строго после G6 (бренд) и G7/G8 (структура), до G10 (хай-фай). Нельзя изобретать UI-язык внутри макета.
**Exit:** все разделы — решениями, не исследованием · контраст AA (с таблицей) · токены точны · светлая/тёмная заданы · язык применён к ≥3 ключевым экранам · связь с брендом G6 и ICP G3 явна · согласован.

### G10 — Хай-фай прототип и приёмка визуала
**Вопрос:** Работает ли продукт как цельный визуальный опыт? · **Документ:** `10_proto_hi.md` · **Режим:** решения · **Под-скилл:** `prototype` (fidelity=hi)
Вызови `prototype` с входом: лоу-фай (G8), UI-язык (G9), бренд (G6), финальные тексты ключевых экранов. Возвращает: хай-фай прототип + эталонный раздел с настоящим текстом + приёмку визуала.
⚠️ **Потолок (П1):** хай-фай доводит **ключевые** экраны до эталона (first value + 1–2 целевых), не все.
**Exit:** ключевые Must-экраны в хай-фай с применённым языком G9 и знаком G6 · эталонный раздел с настоящим текстом · пустые/error/loading визуально · приёмка стейкхолдером · зафиксировано: прототип — источник вида/копирайта, не контракт поведения (поведение в G11+).

### G11 — Концепция архитектуры
**Вопрос:** Как продукт работает как система? · **Документ:** `11_architecture.md` · **Режим:** решения · **Жёсткость:** технически строгая
Темы: стек (с обоснованием); компоненты и потоки данных; модель данных (сущности, связи, ownership, lifecycle); API-дизайн; инфраструктура (хостинг, CI/CD, среды); внешние зависимости (лимиты, SLA, lock-in, fallback, стоимость замены); NFR; **ADR** для каждого дорогого/необратимого решения; **контракты машин состояний** для денег/доступа/удаления.
**Исследования:** `stack-comparison.md`, `api-limits.md`.
**Exit:** архитектура под потоки из G7 · зависимости с fallback или risk acceptance · x10/x100 без переписывания · каждое дорогое решение имеет ADR · модель данных покрывает G4 · для платёжного контура — отдельная ветка на каждый адаптер (у провайдеров разная механика: вебхук vs нет, частичный возврат vs нет).

### G12 — Техническая реализуемость (спайки)
**Вопрос:** Нет ли критического риска, из-за которого концепция не сработает? · **Документ:** `12_spikes.md` · **Режим:** решения · **Жёсткость:** технически строгая
**Принцип:** документ не доказывает реализуемость — нужен **реальный код-спайк**.
Темы: реестр техрисков; спайки (минимальный код); пробные интеграции (реально вызвать API); проверка библиотек; бенчмарки; выводы и влияние на G11.
**На выходе:** код спайков (`research/spikes/`).
**Exit:** каждый P0 техриск из G11 проверен спайком/интеграцией · результаты задокументированы · провал → G11 пересмотрена · ключевые внешние API реально вызваны.

### G13 — Безопасность, данные и юридические условия
**Вопрос:** Можно ли законно и безопасно использовать продукт? · **Документ:** `13_security.md` · **Режим:** факты → решения · **Можно сократить:** pet-проекты
Темы: категории данных; threat model (assets, trust boundaries, attack paths, abuse cases, mitigations); жизненный цикл данных; auth/authz; юрисдикция (152-ФЗ/GDPR, согласия, трансграничная передача); форма собственности; лицензии зависимостей; документы для пользователей.
**Исследования:** `legal-requirements.md`.
**Exit:** критические trust boundaries видимы · P0 security risks с mitigation · legal с юрисдикцией и датой · вопросы к юристу не выданы за заключение · data lifecycle определён.

### G16 — Дорожная карта реализации

## Под-скиллы (оркестрация)

GRILL MI MAX владеет **гейтами и сквозной согласованностью**. Проработку бренда, визуала и прототипа делегирует под-скиллам, но не отпускает в свободное плавание.

**Контракт вызова:** (1) **вход** — явный контекст предыдущих гейтов (не «сделай красиво», а «вот бренд G6, флоу G7, фиделити=hi»); (2) **границы** — под-скилл работает только внутри своего гейта, под потолком П1; (3) **выход** — ограниченный артефакт + сигнал готовности + самопроверка против exit; (4) **валидация** — GRILL MI MAX сам проверяет артефакт против exit-критериев, не на слово; трассируемость обязательна (бренд служит позиционированию G2; визуал — бренду G6 и ICP G3; прототип покрывает флоу G7); (5) **возврат на рельсы** — закрытие гейта по общему протоколу + согласованность.

Под-скиллы: `brand-identity` (G6), `visual-concept` (G9), `prototype` (G8 lo / G10 hi, параметр `fidelity`). Спеки — рядом (`*-SKILL.md`). Нет под-скиллов как отдельных скиллов → GRILL MI MAX делает их работу сам по тем же контрактам.

## Правила документов
- Документ гейта — компактный бриф (2–4 страницы), решения с обоснованиями; исследования — доказательная база в `research/`. Не смешивать.
- Обновляй по ходу допроса; checkpoint в `_SESSION.json` после каждого решения.
- Маркируй [ФАКТ]/[ГИПОТЕЗА]/[РЕШЕНИЕ]/[РИСК]; язык — русский (если не попросят иначе).
- Нумерация документов = номер гейта (G1→01_, G16→16_).
- **Приняли решение — разнесли везде в ту же итерацию (П3).** Отменённое помечай ссылкой на заменившее.
