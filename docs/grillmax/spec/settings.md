# Блок: Настройки и данные

**Статус:** ✅ согласован · **Экраны:** Н-01 (settings), Н-02 (memory), Н-07 (myPeople · Добавленные люди), Н-08 (delPerson), Н-09 (delAll), Ф-07; помощь Н-04/Н-10…13, идея Н-05, документы Н-06/Н-14…17, рефералы Н-03
**Глубина:** полная · **Полная спека настроек:** `06_ux.md` «Спецификация настроек» §1–9. **Смежное:** `spec/personal-data-recalc.md` (Личные данные), `spec/daily-forecast.md` (уведомления), `referral-model.md`, `agreement-rules.md`.

Настройки — служебный раздел: данные о рождении, память, уведомления, помощь, документы и выход (удаление, отзыв согласия).

## Н-01 · Настройки (`settings`)

**Назначение.** Хаб служебных разделов.

**Структура (текущая IA).**

| Секция | Содержимое |
|---|---|
| **Данные** | карточка «Личные данные» (→ Л-16; точка «нужно действие» при отложенном пересчёте) + карточка «Добавленные люди» (→ Н-07); плашка глубины расчёта (текущий % + «Дополнить») |
| **Уведомления** | «Ежедневный прогноз» (→ С-04) |
| **Помощь** | Поддержка (→ Н-04), У меня идея (→ Н-05) |
| **Память Луноры** | → Н-02 |
| **Документы** | → Н-06 |

🔑 **Удаление живёт там, где лежат данные, а не в отдельном «хабе удаления».** Отдельной секции/экрана «Удаление данных» в настройках больше нет. Удаление своих данных (аккаунта) — кнопка внизу «Личные данные» (→ Н-09). Удаление конкретного человека — внутри его карточки в разделе «Добавленные люди» (→ Н-08). Так список людей получает собственный дом, а не фигурирует только в контексте удаления.

**Три правила, задающие раздел.**
- 🔑 **Дверь на выход не на проходе, но и не спрятана.** «Удалить все мои данные» — приглушённая карточка внизу «Личных данных»; отзыв согласия — в документах.
- 🔑 **Подтверждение поля отдельно от сохранения экрана** (пересчёт общий — кнопка у каждого поля создала бы иллюзию независимых сохранений; см. Л-16).
- 🔑 **Возврат честнее подтверждения словом** там, где действие откатывается (слово набирается на автомате; десять секунд на отмену приходятся на момент осознания ошибки).

## Н-07 · Добавленные люди (`myPeople`)

**Назначение.** Единственное место, где добавленные люди показаны как список для управления (раньше они фигурировали только внутри экрана удаления и слотами в «Сегодня»).

**Состав (текущий прототип, `buildMyPeople`).**
- Назад → Настройки; заголовок «Добавленные люди».
- Лид: «Здесь собраны люди, которых вы добавили. Откройте любого, чтобы посмотреть данные или удалить их вместе со связанными документами.»
- Список людей (`data-person`) → карточка человека Н-08. Удалённые недавно показываются строкой `undo` с обратным отсчётом.
- **Пустое состояние** (`NOPEOPLE`): «Пока вы никого не добавили. Люди появляются здесь, когда вы добавляете их для утренней ленты или совместного разбора.»
- Варианты каталога: `Н-07-1` (есть люди) / `Н-07-2` (пусто).

🔑 **Добавление человека тут не живёт.** На этом экране нет кнопки «Добавить человека» — он только показывает уже добавленных и даёт зайти в карточку. Новых людей заводят через отдельный флоу (мини-онбординг добавления, Л-14 и далее), запускаемый из своих мест («Сегодня» / продающие экраны), а не из раздела управления.

## Н-02 · Память Луноры (`memory`, экран «Что помнит Лунора»)

Факты, которые Лунора извлекла из разговоров (живут отдельно от переписки). Экран: ориентирующий блок (закрываемый) · режим учёта контекста · список записей · удаление всех.

| Элемент | Поведение |
|---|---|
| Режим «Учёт контекста» (`data-mode=on`) | Ответы и прогноз на день персонализируются по записям. |
| Режим «Без учёта контекста» (`data-mode=off`) | Ответы и прогноз строятся **только на расчётах школ**. При выборе `off` **и наличии записей** показывается предупреждение: «Записи не удаляются при смене режима — просто перестают участвовать. Включите обратно — снова будут использоваться». (`MEMMODE`) |
| Запись · ✎ (`data-medit`) | Инлайн-правка: поле с текстом + «Готово» (`data-mok`) / «Отмена». Правка меняет текст записи. |
| Запись · ✕ (`data-mdel`) | Инлайн-подтверждение «Удалить эту запись? Лунора перестанет её учитывать» + «Удалить» (`data-mdelok`) / «Отмена». |
| «Удалить все записи» (`data-pop=mall`) | Открывает шторку Ф-07 с word-confirm. |

**Пусто:** «Лунора пока ничего о вас не запомнила. Записи появятся сами, когда что-нибудь расскажете в чате». Пустое состояние и предупреждение режима пересчитываются по числу оставшихся записей (`memCheck`).

🔑 **Смена режима не удаляет записи** — только перестаёт их учитывать. Удаление — отдельное действие. Учёт контекста влияет на **содержание** ответов и прогноза (`spec/chat.md`, `spec/daily-forecast.md`), не на их наличие.

### Ф-07 · Шторка «удалить все записи»
Ключ `memory`, `sheet=pop`. Необратимое удаление: нужно **ввести слово «удалить»** (word-confirm), затем кнопка подтверждения. Открывается из каталога с предзаполнением (regGo вызывает `popMemDelAll`). 🔑 Word-confirm здесь оправдан — действие необратимо (в отличие от откатываемых правок, где честнее «Отмена»).

## Удаление (Н-09 delAll, Н-08 delPerson)

| Код | Что удаляет | Откуда вход |
|---|---|---|
| `Н-09` delAll | всё (аккаунт целиком) | кнопка «Удалить все мои данные» внизу «Личных данных» (Л-16) |
| `Н-08` delPerson | карточку добавленного человека + связанные документы | карточка человека из раздела «Добавленные люди» (Н-07) |

🔑 **Отдельного экрана-хаба «Удаление данных» нет.** Каждое удаление доступно со своего экрана данных: аккаунт — из «Личных данных», человек — из «Добавленных людей». Это решение Антона (раздел людей не должен существовать только в контексте удаления).

Вместе с данными отзывается согласие на обработку ПД; сведения о платежах (суммы, даты, номера операций) сохраняются по требованиям закона.

**Н-08 · карточка человека — нейтральная.** Экран человека показывает его данные и связанные документы, оранжевый блок-предупреждение стоит **внизу, прямо над кнопкой удаления** (а не сверху), чтобы экран читался как просмотр человека, а не как «экран удаления». Треугольник в блоке убран, текст обезличен («данные этого человека»). Кнопки («Сохранить документы» ghost + «Удалить данные» danger) собраны в один блок `docfoot boxed`, без иконок — так же, как на Н-09.

**Сохранение документов перед удалением (Н-09).**
- «Сохранить документы» собирает **все купленные пользователем разборы в один архив** (`data-save=all` → zip «Лунора — документы.zip»); для удаления одного человека (Н-08) — архив разборов этого человека (`data-save=person`).
- Архив показывается в шторке **Ф-04** (`saveSheet`): карточка файла + два действия — **«Переслать в чат»** и **«Скачать файл»** (плюс «Отмена»). Это финальная точка перед нативным сохранением/отправкой; «Скачать» уходит в системное сохранение (Файлы/Downloads), «Переслать в чат» — в чат мессенджера.
- 🔑 **Сводка собирается из реальных счётчиков — каждая строка независима.** Строка выводится, только если это у пользователя есть: добавленные люди, заметки, переписка, созданные разборы — каждая по своему счётчику (как и дата/город — только если заполнены). Важно: **люди, переписка и заметки могут быть без единой покупки** (первый человек бесплатно, 3 бесплатных вопроса в чате), поэтому их наличие не завязано на покупки.
- 🔑 **Кнопка сохранения зависит только от купленных разборов.** Если разборов нет (docs = 0), сохранять нечего: **не выводятся** ни строка «Созданные документы», ни кнопка «Сохранить документы», а текст не обещает сохранение («После удаления восстановить данные будет нельзя»). Остаётся только «Удалить все мои данные».
- **Что можно иметь без покупок:** **один** добавленный человек (первый — бесплатно; третий слот — платный), бесплатный чат (3 вопроса) и **сформированная из него память Луноры**. Поэтому строки «люди / переписка / заметки» могут присутствовать и у пользователя без единой покупки — просто не будет строки «Созданные разборы» и шага сохранения.
- Варианты каталога: `Н-09-1` (с покупками — есть разборы, несколько человек, сохранение) / `Н-09-2` (без покупок — 1 бесплатный человек, бесплатный чат и память, но разборов и сохранения нет).

🔑 **Правило сводок данных — по типу экрана:**

- **Итоговые сводки (что удалим / что будет затронуто)** — показывают **только заполненные поля**. Незаполненное поле **не выводится совсем** (не строкой «не указано»): есть данные → строка есть, нет → строки нет. Экраны: Н-09 (удалить всё), Н-08 (удалить человека). Так устранена прежняя несогласованность на Н-09 (пустое «Время рождения — не указано» выводилось, а пустой адрес — нет).
- **Проверочные сводки перед действием** — наоборот, **намеренно помечают отсутствие ключевого ввода** («время неизвестно» / «не указано»), потому что его отсутствие меняет результат (глубину разбора) и это последний шанс дополнить. Экраны: О-06 (проверьте данные перед расчётом), Л-17 (проверьте перед пересчётом), К-20 (проверьте ваши данные перед оплатой). Это не нарушение правила, а осознанное исключение.
- **Редактируемые экраны данных** (Л-16 Личные данные) показывают пустое поле вместе с действием «Указать…» — пустое поле здесь приглашение заполнить.

**Назначение.** Сначала дать человеку найти ответ самому (частые вопросы по категориям), и только если не нашёл — вывести на живое обращение. Самопомощь первой, форма второй.

**Состав (текущий прототип).**
- Назад → Настройки; заголовок «Поддержка».
- **Вводный текст** (`d-lede`, двумя строками в одном блоке — иначе `d-lede` рисует разделитель между абзацами): «Ниже мы собрали для вас ответы на популярные вопросы. / Если среди них не нашлось ответа на ваш, напишите нам, и мы поможем разобраться.»
- Секция **«Категория вопроса»** — карточки категорий (`HELP`), **только названия, без подписей и счётчика** (по названию и так понятно, что внутри; счётчик «N вопросов» убран как бесполезный).
- Кнопка **«Написать в поддержку»** (`data-sup=oth`) — **сплошной заливкой** (единственная кнопка на экране).
- Шторка обращения `supBox` (общая, см. ниже).

**Категории частых вопросов (`HELP`).** Пять категорий, каждая — отдельный экран `help-<k>` (`Н-04-1`): заголовок + аккордеон вопрос/ответ (`faq`), внизу «Не нашли ответ» и кнопка **«Связаться с нами»** (`data-sup=<k>`).

| Ключ | Категория | Внутри (кратко) |
|---|---|---|
| `calc` | Расчёты и разборы | знак не как на других сайтах, роль времени, расхождение школ, сроки |
| `pay` | Платежи и документы | оплатил/нет документа, чек, повторное скачивание, двойное списание |
| `data` | Мои данные | уточнить время/место, что даёт имя, ошибка в дате |
| `chat` | Чат и лента | лимит вопросов, память Луноры, время прогноза |
| `invite` | Приглашения и бонусы | что получу за друга, когда начисляется, где взять ссылку |

**Обращение = переход в бота поддержки (`Н-04-2`, `supportBot`).** В приложении **нет отдельной формы/чата**. Кнопка «Написать в поддержку» (и общая на Н-04, и внутри каждой категории) сразу открывает **бота поддержки того мессенджера, где запущено приложение** (Telegram → телеграм-бот, MAX → макс-бот; хост известен приложению). В прототипе это показано экраном-заглушкой `supportBot` в bot-оболочке: шапка «Поддержка Луноры · бот», приветствие бота, строка ввода мессенджера.

🔑 **Решение (Антон):** полноценный чат в приложении сейчас не делаем. Мессенджер уже даёт готовый чат, историю, уведомления и вложения — дублировать их в приложении бессмысленно, а форма-посредник только добавляет шаг.

**Контекст — через deep-link, не через форму.** Тема обращения уходит стартовым параметром ссылки на бота (`?start=<topic>`), бот открывается уже зная, кто пришёл и по какому поводу, и первым сообщением приветствует по теме («Вижу, что вы пишете по теме „Платежи и документы“…»). Категория, из которой нажали, становится темой; с общей кнопки — без темы. В прототипе тему хранит `SUPTOPIC`, подпись темы — `SUP_TOPIC`.

🔑 **Ничего «не прикладываем».** Личность и данные пользователя поддержка видит автоматически (id мессенджера → аккаунт), поэтому в копирайте нет фраз вида «приложим номер профиля» — это лишний шум в чувствительной нише. Пользователю не нужно повторять свои данные.

🔑 **Самопомощь раньше обращения.** Категории FAQ стоят до кнопки; живой диалог — запасной путь.

🔑 **Копирайт FAQ про приглашения мирроит экран рефералов** (час за друга + лестница наград), а не формулировку `referral-model.md` («сутки диалога, после первой покупки»). Это то же расхождение, что отмечено в `Н-03` ниже — при финализации реферальной модели синхронизировать оба места.

**Для реализации:** нужен отдельный бот поддержки на каждый мессенджер, где живёт приложение; из Mini App открывается deep-link в чат бота (Telegram — `openTelegramLink`, MAX — аналог) со стартовым параметром темы.

## Н-05 · У меня идея (`idea`)

**Назначение.** Канал предложений от пользователей: человек описывает, чего не хватает или что улучшить, и видит, что идеи действительно доходят до реализации.

**Состав (текущий прототип).**
- Назад → Настройки; заголовок «У меня идея!».
- **Вводный текст** (`d-lede`, без нижней линии-разделителя перед полем): «Мы стараемся сделать Лунору как можно удобнее и полнее. / Если у вас возникла идея, как улучшить сервис или что-то добавить, расскажите нам. Мы обязательно рассмотрим вашу идею.»
- **Форма** (`Н-05-1`, `#ideaForm`): поле ввода (плейсхолдер «Опишите вашу идею») + кнопка **«Отправить идею»** (неактивна, пока поле пустое).
- **«Реализованные идеи»** — блоки-карточки (без статус-плашек): заголовок + описание на 3–4 строки, что за фича и чем полезна. В прототипе две для примера (фаза луны в ленте; своё время ежедневного прогноза).

**Отправка и подтверждение.**

| Элемент | Поведение |
|---|---|
| «Отправить идею» (`data-ideasend`) | Поднимает **шторку** `Ф-13` (`ideaSheet`); содержимое экрана не меняется. Форма за шторкой сбрасывается (поле очищается, кнопка снова неактивна). |
| Шторка `Ф-13` | «Спасибо за идею! Мы обязательно её рассмотрим. Всё, что мы реализуем, появится в списке на этом экране.» Кнопка **«Готово»** (`data-sheet=close`) закрывает шторку. |

🔑 **Подтверждение — стандартной шторкой, а не подменой экрана.** Единый приём для всех подтверждений в приложении (как «Понятно»/«Готово» в других шторках): пользователь не теряет контекст экрана, после «Готово» видит ту же форму, уже чистую.

🔑 **«Реализованные идеи» — доказательство, что канал живой.** Показываем не статусы заявок («прочитали»/«думаем»), а готовые фичи с понятным описанием пользы. Это обещание из шторки («появится в списке») подкреплено реальными примерами.

**Крайние случаи.** Пустое поле — кнопка неактивна, отправка невозможна. Список реализованных идей не бывает пустым в проде (есть что показать с запуска); при необходимости — обычный пустой список.

**Флоу отзыва согласия (Н-14 → Н-19 → Н-09).** Решение (Антон): не кидать с экрана-документа сразу в общий экран удаления.
- **Н-14** (документ «Согласие на ПД») — секция «Отзыв согласия»: одна строка + **нейтральная** кнопка «Отозвать согласие» → Н-19. Оранжевой плашки с последствиями здесь больше нет.
- **Н-19** (`consentRevoke`) — отдельный экран-прослойка: отвечает на **«почему отзыв = удаление»** (по закону без согласия хранить данные нельзя → прекращаем обработку и удаляем карту, разборы, заметки; восстановить нельзя; сохраняются только сведения о платежах). Кнопка «Перейти к удалению данных» → Н-09.
- **Н-09** (`delAll`) — исполнение: сохранить документы заранее, финальное красное подтверждение (шторка word-confirm — ввод слова «удалить»). После подтверждения аккаунта больше нет, поэтому пользователь возвращается на **первый экран бота** (`Б-01`, «Бот · первый вход») — как при самом первом запуске.

🔑 **Два смысла разведены без дублирования:** Н-19 — правовая причина и намерение, Н-09 — механика и необратимое подтверждение. Два шага оправданы необратимостью действия.
