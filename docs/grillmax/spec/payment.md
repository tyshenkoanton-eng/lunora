# Блок: Оплата

**Статус:** ✅ согласован · **Глубина:** полная · **Экраны:** К-20…25 (подтверждение, страница оплаты, результат, проверка, копия чека), К-01…19 (касса · путь платежа), К-09…15 (платежи и чеки), Х-01/Х-03/Х-04 (сбои), сообщения бота Б-09/10/17
**Связанные доки:** `payment-pdf-flow.md`, `receipts.md` (чеки, фискализация), `idempotency.md` (идемпотентность, холд/списание), `refunds.md`.

Платёж — самый чувствительный контур ниши: главный барьер покупателя и есть недоверие к оплате. Принцип: **холд при оплате, списание в момент оказания услуги**, и честное поведение во всех сбоях.

## Подтверждение и оплата (К-20…К-24)

| Экран | Код | Назначение |
|---|---|---|
| Подтверждение | `К-20` payConfirm | сводка заказа перед оплатой; варианты `К-20-1…4` |
| Страница оплаты | `К-21` payGate | платёжная форма оператора (ЮKassa) |
| Оплата подтверждена | `К-22` payOk | успех |
| Проверяем оплату | `К-24` payWait | идёт проверка статуса |
| Оплата не прошла | `К-23` payErr | отказ |

**К-20 · payConfirm — «Проверьте ваши данные».** Сводка-карточка: документ (напр. «Индивидуальный разбор личности · PDF») + **данные для расчёта** (ФИО, дата, время, место). 🔑 **Показываются только реально введённые данные** — адрес и точное время появляются, когда они есть; это **последняя точка, где ошибку ещё можно заметить** перед оплатой. Строка «Оплачивая, вы принимаете [оферту]» (`data-go=doc-offer`). Кнопка «Перейти к оплате · N ₽» → payGate. Назад → pdfSell.
Варианты задаются машиной состояний (`PDFST`/`PAYST`, см. ниже): `К-20-2` «Документ уже куплен» (bought), `К-20-3` «Платёжная система недоступна» (gate), `К-20-4` «Платёж обрабатывается» (hold).

**К-21 · payGate — страница оператора.** `SHELL.payGate = 'web'` — экран оформлен как **внешняя страница платёжного оператора** (логотип ЮKassa, сумма, `ИП … · заказ LN-…`). Способы: банковская карта / СБП / SberPay; форма карты; «Запомнить карту». Кнопка «Оплатить N ₽» (`data-payres=ok`), «Отменить и вернуться в приложение» (`cancel`). Приписка «Данные карты не попадают к продавцу». В прототипе — тестовые переключатели `decline` (оплата не прошла) и `wait` (вернулся раньше).

**К-24 · payWait — «Проверяем оплату».** 🔑 **Приложение можно закрыть** — как придёт подтверждение, Лунора напишет в чат. «Если подтверждение не придёт за десять минут, деньги вернутся автоматически.» Номер заказа + «Написать нам» (help-pay). Действия: «Проверить ещё раз» → payOk, «Вернуться к разборам» → shop.

**К-22 · payOk — «Оплата подтверждена».** «Готовы приступить к сборке документа — не более минуты.» Кнопки «Собрать документ» (→ docBuild) + «Открыть чек» (`data-recopen`). Hold-вариант перекрывает экран боксом «Платёж обрабатывается».

**К-23 · payErr — «Оплата не прошла».** «Если деньги всё же списались, они вернутся автоматически в течение суток.» «Повторить оплату» → payGate, «Вернуться к описанию» → pdfSell, «Написать нам» (help-pay) с номером заказа.

🔑 **Отдельного экрана «Копия чека» (бывш. К-25 payContact) больше нет.** Действия с чеком сведены к двум: **«Скачать»** (`data-save=receipt` → сохранить PDF на устройство) и **«Переслать»** (`data-share=receipt` → системный лист устройства: отправить файл чека в любой чат или на почту самому). Прежнее «Получить копию» дублировало «Переслать» (оба — «отправить чек куда-то»), но тянуло лишний экран с вводом почты; для ККТ чек и так уходит на телефон/почту в момент покупки, так что отдельный ре-сенд не нужен.

## Касса · путь платежа (К-01…К-19)

Полный путь через внешнюю платёжную форму и приложение банка, со всеми развилками возврата.

| Код | Ситуация |
|---|---|
| `К-01` | уход из приложения в кассу |
| `К-02` | страница оплаты |
| `К-03` | приложение банка |
| `К-04` | оплата прошла |
| `К-05` | ждём банк |
| `К-06` | не вернулся в приложение |
| `К-07` | банк отклонил |
| `К-08` | вернулся через час |
| `К-18` | платёж пока не найден |
| `К-19` | нашёлся при проверке |

🔑 Ключевой риск — «ушёл оплачивать и не вернулся» / «заплатил, а подтверждение не дошло». Все эти состояния подаются так, чтобы человек понимал: деньги в безопасности, статус проверяется.

## Платежи и чеки (К-09…К-15)

| Код | Экран |
|---|---|
| `К-09` | История платежей |
| `К-10` | Один платёж |
| `К-12` | Чек: `К-12-1` самозанятый (НПД) / `К-12-2` ИП с кассой (ККТ) |
| `К-11` | Возвращённый платёж (аннулированный чек + чек возврата для ККТ) |
| `К-15` | Возврат одобрен |

Чек-карточка (`receiptCard`) имеет три вида: обычный `pay`, аннулированный `void` (НПД — пунктирная рамка), возврат `refund` (ККТ — отдельный чек возврата). Фискализация и форма чека — `receipts.md` (две схемы: НПД 422-ФЗ и ККТ 54-ФЗ). Возвраты — `refunds.md`.

🔑 **К-10 содержит только то, что необходимо по закону.** Единственный обязательный артефакт — фискальный чек; он показан на экране целиком (все реквизиты + QR) с действиями «Скачать / Переслать» (исполнение обязанности выдать чек). Поэтому на экране **нет** дублирующего блока-сводки «Что оплачено / Дата / Способ / Номер операции / Заказ» (всё это уже на чеке; банк и внутренний номер заказа — вообще не фискальные реквизиты), **нет** «Написать в поддержку» (поддержка — в настройках). Остаётся заголовок-ориентир (название покупки + сумма/статус), ссылка на сам разбор карточкой в стиле «связанный документ» (секция «Документ» перед чеком — удобство, ведёт к купленному разбору) и сам чек.

🔑 **К-11 (возврат) — то же правило.** Лишний дубль-сводки `.calc` и кнопка «Написать в поддержку» убраны (как на К-10). Остаётся: заголовок-статус, блок «Деньги вернулись на карту ···6411 · 1–3 рабочих дня» (суть экрана возврата — куда и когда вернулись деньги, на чеке этого нет), сноска «разбор больше недоступен», сами фискальные документы возврата (НПД — аннулированный чек; ККТ — аннулированный + чек возврата) и сноска про их механику.

## Машина нештатных состояний (`payStateFor`)

Нештатные экраны не отдельные ключи, а **наложения** на обычный экран, выбираемые по двум переменным:

- **`PDFST`** (состояние купленного PDF) — приоритетнее: `bought` → на payConfirm/pdfSell бокс «Документ уже куплен» (платить второй раз не нужно, файл в «Мои разборы»); `stale` → на prodResult бокс «Данные изменились» (уточнили данные → пересобрать бесплатно).
- **`PAYST`** (ход платежа) — `hold` → payOk/payWait показывают «Платёж обрабатывается»; `gate` → payConfirm показывает «Платёжная система недоступна» (деньги не списаны, заказ сохранён); `norec` → К-12 «Чек ещё формируется»; `nodoc` → docBuild рисуется обычно, сбой наступает по ходу (`null`-значение).

`stale` связывает оплату с блоком «Личные данные → пересчёт» (`spec/personal-data-recalc.md`): после пересчёта купленный документ помечается требующим бесплатной пересборки.

## Ключевые правила (реализовать точно)

- **Холд, не списание, при оплате.** Списание — в момент выдачи результата (совпадает с оказанием услуги; `idempotency.md`).
- **Условия сделки показаны до оплаты** (на экране глубины prodDepth, ст. 10 ЗоЗПП), оферта акцептуется кнопкой оплаты.
- **Идемпотентность:** повторная оплата/двойное списание ловятся и возвращаются **до** обращения пользователя.
- **Чек** выставляется по применимой схеме (НПД/ККТ), доставляется в Telegram или на почту; при задержке — статус «чек ещё формируется», не ошибка.
- **Купленное не продаётся повторно:** bought-состояние ведёт к открытию документа, а не к новой оплате.
